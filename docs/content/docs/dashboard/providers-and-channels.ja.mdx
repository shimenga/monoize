---
title: Provider と Channel
description: Group 内で順序付けた Provider と内蔵 Channel で上流ルートを定義します。
---

保存した Provider の順序は、キャッシュの有効期限を待たずに反映されます。既存の Channel バインディングとアフィニティのルールは引き続き適用されます。

## 概念

- **Provider（プロバイダー）** は 1 つの Group に属します。ルーティング順序、既定価格、ヘルスポリシー、順序付き変換チェーンを定義します。
- **Channel（チャネル）** は Provider が持つ唯一の上流エンドポイントです。上流タイプ、ベース URL、認証情報、モデル対応付け、タイムアウトを保持します。

リクエストはまず Provider を選択し、その中の Channel を選択します。選択規則は[ルーティングと信頼性](/ja/docs/routing)を参照してください。

## Provider を作成

1. サイドバーの**プロバイダー**を開きます。
2. 作成ボタンをクリックして名前を入力します。
3. 1 つの Group を選択し、内蔵 Channel を設定します。
4. Provider 名と Channel 名を公開ページに表示できることを確認します。
5. 既定値が合わない場合は `channel_max_retries` と `channel_retry_interval_ms` を設定します。
6. 明確な理由がない限り、`circuit_breaker_enabled` は有効のままにします。

## Channel を設定

1. Provider を開き、**Channel** を選択します。
2. 上流タイプを選択します：`responses`、`chat_completion`、`messages`、`gemini`、`openai_image`、`replicate`。
3. 上流のベース URL と API キーを入力します。
4. 任意：`proxy_url` を設定して、プロセスレベルの上流プロキシを上書きします。

後で Channel を編集するとき、API キー欄を空にすると保存済みのキーが維持されます。

## セッションキャッシュヘッダー

Channel で**自動セッションアフィニティ**を設定すると、転送する各リクエストに安定したセッション識別子を付けます。

この設定が `null` のとき、Monoize は次のベース URL で自動的に有効にします。

- Cloudflare Workers AI: `https://api.cloudflare.com/client/v4/accounts/{account_id}/ai`（任意の `/v1`）
- OpenCode Zen または OpenCode Go: `https://opencode.ai/zen` とその配下のパス

有効なとき、Monoize は同じ値で次の 2 つのヘッダーを送ります。

- `x-session-affinity`
- `x-opencode-session`

値の優先順位は次のとおりです。Channel の追加ヘッダーにある上記いずれかの名前、クライアントヘッダー（`session_id`、`session-id`、`x-session-id`、`x-opencode-session`、`x-session-affinity`）、本文の会話 ID、`prompt_cache_key`、最後に会話先頭のハッシュです。

OpenCode Go は `x-opencode-session` でプロンプトキャッシュをセッションに結びます。このヘッダーがないリクエストは失敗することがあります。

OpenCode Zen または OpenCode Go への生存プローブでは、Channel の追加ヘッダーにこれらの名前がないとき、リテラル値 `mono-probe` を送ります。

## Channel をテスト

Channel を開き、順次テストまたは同時テストを実行します。

テストは出力上限 16 token の短いストリーミング補完を送ります。HTTP 2xx だけでは不十分です。ストリームはプロトコルの終端イベントに到達する必要があります。

Responses Channel では、`response.completed` は合格です。error オブジェクトがない `response.incomplete` も合格です。推論モデルは 16 token 上限に達して `incomplete` を返すことがあります。その結果でも Channel には到達できています。

## モデルを対応付け

内蔵 Channel は、提供する論理モデルを列挙します。モデル対応付けの内容：

- `redirect`：実際の上流モデル名。空にすると論理名をそのまま送信します。
- 価格 Profile モード：Provider の既定値を継承、上書き、または未価格設定にします。
- 任意の倍率上書き。未設定の場合は Provider の倍率を継承します。

Channel が有効で、モデル対応付けに完全な価格がある場合のみ、そのモデルはその Provider にルーティングされます。

価格警告が表示されても Provider を保存できます。各警告の論理モデルと不足している usage class を確認します。トラフィックを送る前に不足レートを追加します。

## Provider の変換

Provider は順序付き変換ルールのリストを保持できます。Provider の選択後、上流エンコードの前に、その Provider が処理するすべてのリクエストに適用されます。[変換](/ja/docs/transforms)を参照してください。

## 卸売 Provider

`agent`（代理）グループは代理アカウント向けで、通常の Provider を持ちません。

1. 先に `agent` クラスの Group を作成します。**プロバイダー**ページで**カタログ範囲**を `agent` に切り替えて作成するか、代理グループが存在しない場合は卸売ダイアログ内で直接作成できます。
2. **卸売プロバイダーを追加**をクリックします。
3. `standard`、`enterprise`、`private` のいずれかのクラスに属する既存の Provider をソースとして選択します。
4. ソースの Channel 設定とモデルマッピングを一度だけコピーします。コピー後は独立し、ソースの変更は反映されません。
5. 各モデルの倍率は既定でソースの倍率と同じです。保存前に任意の倍率を変更できます。後から通常の Provider エディターでも編集できます。
6. 卸売 Provider はソースの Billing Profile を再利用し、独自の倍率で卸売価格を決めます。

代理アカウントだけが代理グループを表示し、その中で API key を作成し、その倍率を利用できます。代理アカウントのモデルマーケットは他のクラスと同じ規則に従います。

## グループ

各 Provider は 1 つの Group に属します。API キーは許可された Group の Provider のみにルーティングされます。Group を使ってユーザー層や環境を分離します。

Group を作成または改名するときは、公開表示を確認します。公開モデルマーケットとステータスページには、確認済みの Group、Provider、Channel 名が表示されます。
